审查用户提供的固定点与 `HEAD` 之间的差异，分为两个轴：

- **标准**——代码是否符合本仓库记录的编码标准？
- **规范**——代码是否忠实实现了发起该变更的问题/规范？

两个轴作为**并行子代理**运行，避免相互污染上下文，然后由此 skill 汇总它们的发现。

你应该已获得问题跟踪器——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比较点

用户所说的内容就是固定点——可以是提交 SHA、分支名、标签、`main`、`HEAD~5` 等。如果用户没有指定，请询问。

只记录一次差异命令：`git diff <fixed-point>...HEAD`（三个点，因此比较基于 merge-base）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点可解析（`git rev-parse <fixed-point>`）且差异非空。错误引用或空差异应在这里失败，而不是在两个并行子代理内部失败。

### 2. 确定规范来源

按以下顺序查找发起该变更的规范：

1. 提交消息中的问题引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规范文件。
4. 如果找不到，询问用户规范在哪里。如果用户说没有规范，**规范**子代理将跳过并报告“无可用规范”。

### 3. 确定标准来源

仓库中任何记录代码编写方式的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库记录的内容外，标准轴始终包含下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（_Refactoring_，第 3 章），即使仓库没有记录任何内容也适用。它受以下两条规则约束：

- **仓库标准优先。** 已记录的仓库标准始终优先；如果它认可基线会标记的做法，则抑制该坏味道。
- **始终是判断。** 每种坏味道都是带标签的启发式判断（“可能存在 Feature Envy”），绝不是硬性违规——与此处任何标准一样，跳过工具已经强制执行的内容。

每种坏味道都说明*它是什么* → *如何修复*；将其与差异对照：

- **神秘命名（Mysterious Name）**——函数、变量或类型的名称无法说明其作用或所保存的内容。→ 重命名；如果找不到诚实的名称，说明设计含混不清。
- **重复代码（Duplicated Code）**——变更中有多个代码块或文件出现相同的逻辑结构。→ 提取共享结构，让两处都调用它。
- **特征依恋（Feature Envy）**——某个方法访问另一个对象的数据多于自身数据。→ 将方法移到它依恋的数据上。
- **数据泥团（Data Clumps）**——同几项字段或参数总是一起传递（它们需要诞生为一个类型）。→ 将它们封装成一个类型，并传递该类型。
- **基本类型偏执（Primitive Obsession）**——用基本类型或字符串代替本应拥有独立类型的领域概念。→ 为该概念提供一个小型独立类型。
- **重复的分支切换（Repeated Switches）**——针对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 用多态替代，或让两处共享一个映射。
- **霰弹式修改（Shotgun Surgery）**——一个逻辑变更迫使差异中的许多文件分散修改。→ 将相关变更集中到一个模块中。
- **发散式变化（Divergent Change）**——同一文件或模块因多个无关原因被编辑。→ 拆分，使每个模块只因一个原因变化。
- **投机式泛化（Speculative Generality）**——为规范未提出的需求添加抽象、参数或钩子。→ 删除；内联回去，直到真实需求出现。
- **消息链（Message Chains）**——调用方不应依赖的长串 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法封装这段访问过程。
- **中间人（Middle Man）**——主要只是继续向下委托的类或函数。→ 删除它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**——子类或实现者忽略或覆盖了继承的大部分内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

**标准子代理提示词**——包括：

- 完整的差异命令和提交列表。
- 第 3 步找到的标准来源文件列表，**以及完整粘贴的第 3 步坏味道基线**——子代理无法通过其他途径访问它。
- 任务说明：“按相关文件/代码块报告——（a）差异违反已记录标准的所有位置：引用标准（文件及规则）；（b）发现的任何基线坏味道：命名并引用代码块。区分硬性违规与判断——已记录标准的违反可以是硬性问题，但基线坏味道始终是判断，且已记录的仓库标准优先于基线。跳过工具已强制执行的内容。不超过 400 个单词。”

**规范子代理提示词**——包括：

- 差异命令和提交列表。
- 规范的路径或获取到的内容。
- 任务说明：“报告：（a）规范要求但缺失或不完整的需求；（b）差异中未被要求的行为（范围蔓延）；（c）看似已实现但实现可能有误的需求。每条发现都引用规范原文。不超过 400 个单词。”

如果缺少规范，跳过规范子代理，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下呈现两份报告，原样呈现或做轻微清理。**不要**合并或重新排序发现——两个轴特意保持分离（见 _为什么分为两个轴_）。

以单行摘要结尾：分别给出每个轴的发现总数，以及每个轴中最严重的问题（如有）。不要在两个轴之间选出唯一胜者——分离两个轴正是为了避免这种重新排序。

## 为什么分为两个轴

一次变更可能通过一个轴，却未通过另一个轴：

- 遵循所有标准却实现了错误的功能 → **标准通过，规范失败。**
- 完全实现了问题要求却破坏了项目约定 → **规范通过，标准失败。**

分别报告可以防止一个轴掩盖另一个轴。
