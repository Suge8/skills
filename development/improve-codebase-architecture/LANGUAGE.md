# 语言

这是这个 skill 提出每条建议时使用的共享词汇。精确使用这些术语，不要替换成“组件”“服务”“API”或“边界”。语言一致性就是重点。

## 术语

**模块**
任何有接口和实现的东西。刻意不绑定尺度，同样适用于函数、类、包，或跨层级的功能切片。
_避免_：单元、组件、服务。

**接口**
调用方为了正确使用模块而必须知道的一切。包括类型签名，也包括不变量、顺序约束、错误模式、必需配置和性能特征。
_避免_：API、签名（太窄，只指类型层面的表面）。

**实现**
模块内部的代码。它不同于**适配器**：一个东西可以是小适配器、大实现（Postgres repo），也可以是大适配器、小实现（in-memory fake）。讨论接缝时使用“适配器”；其他时候使用“实现”。

**深度**
接口处的杠杆收益，也就是调用方（或测试）每学习一单位接口能触达多少行为。当大量行为藏在小接口之后，模块就是**深**的。当接口几乎和实现一样复杂，模块就是**浅**的。

**接缝** _(来自 Michael Feathers)_
一个可以改变行为而不用在原处编辑的地方。也就是模块接口所在的*位置*。选择把接缝放在哪里，本身就是一个设计决策，独立于接缝背后放什么。
_避免_：边界（和 DDD 的 bounded context 含义过载）。

**适配器**
在接缝处满足接口的具体东西。它描述的是*角色*（填哪个槽位），不是实体构成（里面有什么）。

**杠杆收益**
调用方从深度中得到的东西。调用方每学习一单位接口，就获得更多能力。一个实现可以在 N 个调用点和 M 个测试中反复回本。

**局部性**
维护者从深度中得到的东西。变更、缺陷、知识和验证集中在一处，而不是扩散到调用方。修一次，到处都修好。

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小的、可 mock、可替换的部分组合而成，只是这些部分不属于接口。模块既可以有**内部接缝**（实现私有，供自身测试使用），也可以在接口处有**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂性消失，说明模块没有隐藏任何东西（它只是传递层）。如果复杂性在 N 个调用方中重新出现，说明模块确实有价值。
- **接口就是测试表面。** 调用方和测试跨越同一条接缝。如果你想测试到接口之后，模块的形状很可能不对。
- **一个适配器意味着假想接缝。两个适配器才意味着真实接缝。** 除非接缝两侧确实有变化，否则不要引入接缝。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，相对于它的**接口**来衡量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处，并满足**接口**。
- **深度**为调用方带来**杠杆收益**，为维护者带来**局部性**。

## 被拒绝的表述方式

- **把深度理解为实现行数与接口行数之比**（Ousterhout）：这会奖励给实现灌水。我们使用“深度即杠杆收益”。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的 public methods**：太窄，这里的接口包括调用方必须知道的每个事实。
- **“边界”**：和 DDD 的 bounded context 含义过载。说**接缝**或**接口**。
