# 加深

在给定依赖关系的前提下，如何安全地加深一组浅模块。本文假定你使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估一个加深候选时，先分类它的依赖。类别决定加深后的模块如何跨接缝测试。

### 1. 进程内

纯计算、内存状态、无 I/O。总是可以加深，把这些模块合并，并直接通过新接口测试。不需要适配器。

### 2. 本地可替换

有本地测试替身的依赖（Postgres 用 PGLite，文件系统用 in-memory filesystem）。如果替身存在，就可以加深。加深后的模块在测试套件中带着替身运行。接缝是内部的，不在模块外部接口上开端口。

### 3. 远程但自有（端口与适配器）

你自己的跨网络边界服务（microservices、internal APIs）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑；传输作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/queue 适配器。

推荐表述：*“在接缝处定义一个端口，为生产实现 HTTP 适配器，为测试实现内存适配器，让逻辑集中在一个深模块中，即使它部署时跨越网络。”*

### 4. 真外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入端口接收；测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假想接缝。两个适配器才意味着真实接缝。** 除非至少两个适配器有正当理由（通常是生产 + 测试），否则不要引入端口。只有一个适配器的接缝只是间接层。
- **内部接缝 vs 外部接缝。** 一个深模块可以有内部接缝（实现私有，供自身测试使用），也可以在接口处有外部接缝。不要因为测试使用内部接缝，就把内部接缝暴露到接口上。

## 测试策略：替换，不叠加

- 一旦加深后模块的接口上有了测试，旧的浅模块单元测试就变成浪费，删除它们。
- 在加深后模块的接口上写新测试。**接口就是测试表面**。
- 测试断言通过接口可观察到的结果，而不是内部状态。
- 测试应该能经受内部重构，它们描述行为，不描述实现。如果实现变化时测试也必须变化，它就是测试越过了接口。
