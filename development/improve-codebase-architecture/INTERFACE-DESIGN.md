# 接口设计

当用户想为一个已选中的加深候选探索替代接口时，使用这个并行子代理模式。它基于 “Design It Twice”（Ousterhout），你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**、**杠杆收益**。

## 流程

### 1. 框定问题空间

启动子代理之前，先为选中的候选写一段面向用户的问题空间说明：

- 任何新接口必须满足的约束
- 它会依赖哪些东西，以及这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图，用来让约束具体化。它不是提案，只是让约束落地

把这些展示给用户，然后立即进入第 2 步。用户阅读和思考时，子代理并行工作。

### 2. 启动子代理

使用 Agent tool 并行启动 3 个以上子代理。每个子代理都必须为加深后的模块产出一个**根本不同**的接口。

给每个子代理单独的技术 brief（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝后面放什么）。这个 brief 独立于第 1 步面向用户的问题空间说明。给每个代理不同的设计约束：

- Agent 1：“最小化接口，目标是最多 1–3 个入口点。最大化每个入口点的杠杆收益。”
- Agent 2：“最大化灵活性，支持许多用例和扩展。”
- Agent 3：“为最常见的调用方优化，让默认场景极其简单。”
- Agent 4（如果适用）：“围绕端口与适配器，为跨接缝依赖做设计。”

在 brief 中同时包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，让每个子代理都用架构语言和项目领域语言一致地命名事物。

每个子代理输出：

1. 接口（types、methods、params，以及 invariants、ordering、error modes）
2. 展示调用方如何使用它的 usage example
3. 实现会在接缝后隐藏什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡，哪里杠杆收益高，哪里薄弱

### 3. 展示并比较

按顺序展示各个设计，让用户能消化每一个，然后用 prose 比较它们。按**深度**（接口处的杠杆收益）、**局部性**（变更集中在哪里）和**接缝位置**做对比。

比较后给出你自己的推荐：你认为哪个设计最强，为什么。如果不同设计中的元素能很好组合，提出一个混合方案。要有立场，用户要的是强判断，不是菜单。
