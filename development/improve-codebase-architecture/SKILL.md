# 改进代码库架构

暴露架构摩擦，并提出**加深机会**，也就是把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

## 术语表

每条建议都精确使用这些术语。语言一致性就是重点，不要漂移到“组件”“服务”“API”或“边界”。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **模块**，任何有接口和实现的东西（函数、类、包、功能切片）。
- **接口**，调用方使用模块必须知道的一切：类型、不变量、错误模式、顺序、配置。不只是类型签名。
- **实现**，内部代码。
- **深度**，接口处的杠杆收益：小接口背后有大量行为。**深** = 高杠杆收益。**浅** = 接口几乎和实现一样复杂。
- **接缝**，接口所在的位置；一个可以改变行为而不用原地编辑的地方。（用这个词，不要用“边界”。）
- **适配器**，在接缝处满足接口的具体东西。
- **杠杆收益**，调用方从深度中得到的东西。
- **局部性**，维护者从深度中得到的东西：变更、缺陷、知识集中在一处。

关键原则（完整列表见 [LANGUAGE.md](LANGUAGE.md)）：

- **删除测试**：想象删除这个模块。如果复杂性消失，它就是传递层。如果复杂性在 N 个调用方中重新出现，它就在发挥价值。
- **接口就是测试表面。**
- **一个适配器意味着假想接缝。两个适配器才意味着真实接缝。**

这个 skill 由项目的领域模型提供信息。领域语言为好的接缝命名；ADR 记录这个 skill 不应该重新争论的决策。

## 流程

### 1. 探索

先阅读项目的领域术语表，以及你触及区域的所有 ADR。

然后使用 Agent tool，以 `subagent_type=Explore` 遍历代码库。不要遵循僵硬的启发式规则，要有机探索，并记录你感受到摩擦的地方：

- 理解一个概念是否需要在许多小模块之间来回跳转？
- 哪些模块是**浅**的，接口几乎和实现一样复杂？
- 哪些纯函数只是为了可测试性被抽出，但真正的缺陷藏在它们如何被调用里（没有**局部性**）？
- 哪些紧耦合模块跨接缝泄漏？
- 代码库哪些部分未测试，或很难通过当前接口测试？

对任何你怀疑浅的东西应用**删除测试**：删除它会集中复杂性，还是只是移动复杂性？“是的，会集中”才是你要的信号。

### 2. 把候选项呈现为 HTML 报告

把自包含 HTML 文件写到操作系统临时目录，避免任何东西落进 repo。临时目录从 `$TMPDIR` 解析，fallback 到 `/tmp`（Windows 用 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都有新文件。为用户打开它，Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`，并告诉用户绝对路径。

报告使用 **通过 CDN 加载的 Tailwind** 做布局和样式，并在图、流程、序列能可靠表达结构时使用 **通过 CDN 加载的 Mermaid** 绘制图表。混合 Mermaid 和手写 CSS/SVG 视觉表达，关系是图结构时（调用图、依赖、序列）用 Mermaid；想要更编辑化的表达时（质量图、剖面图、折叠动画）用手写 div/SVG。每个候选都要有 **前后对比可视化**。要视觉化。

每个候选使用同一模板，但渲染为卡片：

- **文件**，涉及哪些文件/模块
- **问题**，当前架构为什么造成摩擦
- **方案**，用直白中文描述会改变什么
- **收益**，用局部性和杠杆收益解释，以及测试会如何改进
- **前后对比图**，并排、自定义绘制，展示浅薄状态和加深结果
- **推荐强度**，`强`、`值得探索`、`推测性` 之一，渲染成徽章

报告结尾加 **首要推荐** 小节：你会先处理哪个候选，为什么。

**领域使用 CONTEXT.md 词汇，架构使用 [LANGUAGE.md](LANGUAGE.md) 词汇。** 如果 `CONTEXT.md` 定义了 “Order”，就说 “Order intake 模块”，不要说 “FooBarHandler”，也不要说 “Order 服务”。

**ADR 冲突**：如果候选与现有 ADR 冲突，只有当摩擦真实到值得重新打开 ADR 时才暴露。必须在卡片中明确标记（例如警告提示：_“与 ADR-0007 冲突——但值得重新打开，因为……”_）。不要列出 ADR 理论上禁止的每个重构。

完整 HTML 脚手架、图表模式和样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

现在**不要**提出接口。文件写完后，问用户：“你想探索哪一个？”

### 3. 拷问循环

用户选择候选后，进入拷问式对话。和用户一起走设计树，讨论约束、依赖、加深后模块的形状、接缝后面放什么、哪些测试保留。

副作用在决策成形时就地发生：

- **用 `CONTEXT.md` 中没有的概念命名加深后的模块？** 把该术语加入 `CONTEXT.md`，遵循和 `/grill` 文档模式相同的纪律（见 [CONTEXT-FORMAT.md](../grill/CONTEXT-FORMAT.md)）。文件不存在就懒创建。
- **会话中收紧模糊术语？** 当场更新 `CONTEXT.md`。
- **用户用承重理由拒绝候选？** 提供 ADR，措辞为：_“要我把这记录成 ADR，让未来的架构评审不要再次建议它吗？”_ 只有当这个理由真的会被未来探索者用来避免再次建议同一件事时才提供，不记录临时理由（“现在不值得”）和不言自明的理由。见 [ADR-FORMAT.md](../grill/ADR-FORMAT.md)。
- **想探索加深后模块的替代接口？** 见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。
