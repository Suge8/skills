# 逻辑原型

一个让用户亲手驱动状态模型的小终端交互程序。适用于**业务逻辑、状态流转、数据形状**类问题——纸上看着合理、只有推过真实用例才会露馅的那种。

## 什么时候是对的形状

- "不确定这个状态机能不能处理先 X 后 Y 的边界"
- "这个数据模型真的能表达……的情况吗"
- "想在写正式代码前先感受一下 API 该长什么样"
- 一切用户想**按按钮看状态变化**的问题

问题是"该长什么样" → 走错分支了，用 [UI.md](UI.md)。

## 流程

### 1. 写下问题

动手前先在原型文件顶部注释（或原型 README）写清楚：原型的状态模型是什么、要回答什么问题。回答错问题的原型是纯浪费——问题显式写下来，事后才能核对。

### 2. 选语言

用宿主项目的语言和工具链。项目没有明显运行时（如纯文档仓库）就问用户。不为原型引入新的包管理器或运行时。

### 3. 把逻辑隔离成可迁移模块

真正回答问题的逻辑放在一个小而纯的接口后面，验证通过后能直接搬进正式代码。TUI 外壳是扔的，逻辑模块不是。按问题选形状：

- **纯 reducer** —— `(state, action) => state`。动作是离散事件、状态是单值时用
- **状态机** —— 显式状态和迁移。"当前哪些动作合法"本身就是问题时用
- **一组纯函数** 作用于普通数据类型。没有隐式当前状态、只有变换时用
- **带清晰方法面的类/模块**。逻辑确实持有持续内部状态时用

按问题选形状，不按"哪个好接 TUI"选。保持纯净：无 I/O、无终端代码、无控制流 console.log。TUI 引用它并调用它，反方向零依赖——这是原型寿命结束后逻辑还能活下来的原因。

### 4. 搭最小的 TUI 暴露状态

轻量 TUI：每个 tick 清屏（`console.clear()` 或 `\033[2J\033[H`）重绘整帧，用户永远看到一个稳定视图而不是滚动堆积。每帧两部分：

1. **当前状态**，逐字段一行或格式化 JSON。字段名加粗、次要信息（时间戳/ID/派生值）变暗，原生 ANSI 转义即可（`\x1b[1m` 粗 `\x1b[2m` 暗 `\x1b[0m` 重置），不为样式引库
2. **快捷键**列在底部：`[a] 加用户  [d] 删用户  [t] 时钟前进  [q] 退出`

行为：初始化内存状态渲染首帧 → 每次读一个按键分发给 handler → 全帧重绘 → 循环到退出。整帧放得进一屏。

### 5. 一条命令能跑

挂到项目任务运行器；没有任务运行器就把命令写在原型 README 顶部。

### 6. 交给用户开车

给出运行命令，用户自己驱动。有价值的时刻是用户说"等等，这不应该发生"或"咦，我以为 X 会不一样"——那是*想法*里的 bug，正是原型存在的意义。用户要加动作就加，原型会进化。

### 7. 收尾

问题有答案后：验证过的 reducer/状态机/函数组搬进正式模块（决定被吸收）；TUI 外壳和原型文件直接删除，按 [SKILL.md](SKILL.md) 第 6 条规则执行。

## 反模式

- **别写测试**。需要测试的原型已经不是原型
- **别接真实数据库**。除非问题就是持久化，否则用内存 store
- **别泛化**。没有"以后想支持 X 怎么办"，原型只回答一个问题
- **别把逻辑和 TUI 糊在一起**。reducer 里出现 console.log/终端转义码就不可迁移了
- **别把 TUI 外壳带进生产**。值得留的是背后的逻辑模块
