# UI 原型

在一个路由上生成**几个结构迥异的 UI 变体**，底部浮条切换。用户在浏览器里翻着看，挑一个（或各取一块），其余扔掉。

问题是逻辑/状态而不是长相 → 走错分支了，用 [LOGIC.md](LOGIC.md)。

## 什么时候是对的形状

- "这个页面该长什么样？"
- "这个 Dashboard 想先看几个方案再定"
- "设置页换个布局试试"
- 一切用户会在脑内三个模糊 mockup 之间纠结一天的时刻

## 两种子形状——强烈优先 A

UI 变体**贴着真实应用**（真 header、真 sidebar、真数据、真密度）才好评判；孤立的空路由是真空，每个变体单看都不错。有宿主页面就必须用 A，只有真的无处安放才用 B。

**子形状 A —— 挂在现有页面（默认）**：变体渲染在**同一路由**上，`?variant=` 参数门控。现有的数据获取、参数、鉴权全保留，只换渲染子树。要做的东西还没有页面、但天然属于某个页面（Dashboard 新区块、设置页新卡片、现有流程新步骤）→ 仍然是 A，把变体挂进宿主页面。

**子形状 B —— 新路由（万不得已）**：只在原型对象真的没有宿主页面时用（全新顶层界面）。遵循项目路由约定建一次性路由，路径或文件名里带 `prototype` 字样，同样 `?variant=` 模式。动手前自查一次：真的没有页面能嵌吗？

## 流程

### 1. 写下问题，定 N

默认 **3 个变体**，超过 5 个就不再是"迥异"而是噪声。计划一行写在原型位置或文件顶部注释：

> "设置页 3 个变体，现有 /settings 路由上 ?variant= 切换。"

### 2. 生成结构迥异的变体

每个变体都必须遵守：页面的用途和可用数据、项目现有组件库/样式系统、清晰的导出名（`VariantA/B/C`）。

变体必须**结构不同**——不同布局、不同信息层级、不同主操作，而不是换个颜色。三个微调过的卡片网格不是原型，是壁纸。两稿长得太像就重做一稿，并显式加约束（如"禁止卡片网格"）。

### 3. 接线

路由上放一个切换组件：变体条件渲染 + 底部浮条。子形状 A：现有数据获取留在切换组件之上，每个变体只换渲染子树。子形状 B：一次性路由挂同一个切换组件。

### 4. 底部浮条

屏幕底部居中的固定小条：左箭头（循环上一个）、当前变体标签（`B — 侧栏布局`）、右箭头。行为：

- 点击箭头更新 URL 参数（用框架路由的 replace），变体可分享、刷新稳定
- `←` `→` 键盘也能切；焦点在 input/textarea/contenteditable 时不拦截
- 视觉上明显不属于被评审的设计（高对比胶囊 + 阴影）
- 生产构建隐藏——`NODE_ENV !== 'production'` 门控，防止误合并把浮条带给用户

浮条做成一个共享组件，放项目共享 UI 的位置，两种子形状复用。

### 5. 交给用户挑

给出 URL 和 `?variant=` 键。最有价值的反馈通常是**"我要 B 的头部加 C 的侧栏"**——那才是用户真正想要的设计。

### 6. 收尾清理

胜出后把答案（哪个变体、为什么）写进并入 commit 的 message，然后：

- 子形状 A：赢家并入现有页面；输家和浮条直接删除
- 子形状 B：赢家升级为正式路由；一次性路由和浮条直接删除

不留分支不留残留——留在仓库里的变体组件腐烂得很快，还会迷惑下一个读代码的人；值得留的只有结论，它已经活在赢家代码和 commit message 里。

## 反模式

- **只差颜色或文案的变体**。那是微调不是原型，真变体在结构上有分歧
- **变体间共享太多代码**。共享 `<Header>` 可以，共享 `<Layout>` 就失去意义——每个变体要有推翻布局的自由
- **变体接真实写操作**。只读没问题；要写就指向 stub——问题是"长什么样"，不是"后端通不通"
- **原型代码直接晋升生产**。它是在无测试、最小错误处理的约束下写的，并入时要正经重写
