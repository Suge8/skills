# 维护审计手册

`standard` / `deep` 在核心审计之外读取本文件。发现仍使用 [audit-core.md](audit-core.md) 的“Finding format”和排序规则。

## 1. 性能

寻找算法和架构层面的收益，不做未经度量的微优化。

- N+1：循环或列表行中逐项 query / fetch；缺少 batching / dataloader。
- 错误复杂度：对同一集合嵌套扫描；循环里反复 `find` / `filter`，本应预建 Map。
- 缓存缺口：同一请求或渲染反复执行相同昂贵计算 / fetch；稳定数据没有 HTTP 或数据层缓存。只有成本明确时才建议缓存。
- 载荷：`select *`、只需 ID 却传完整对象、无界列表没有分页、大 JSON 发往客户端。
- 前端：重依赖只做小事、低频路由未拆包、图片 / 字体未优化、可在服务端获得的数据又由客户端请求、渲染瀑布。遵循项目框架约定和已有最佳实践。
- 后端：请求线程执行应入队的同步重活；查询模式暗示索引缺失时标记“待验证”，没有 schema 证据不得断言；每请求新建连接而已有连接池。
- 构建 / CI：缓存缺失、步骤重复、可并行测试串行执行。先测量实际耗时。

## 2. 技术债与架构

- 同一逻辑出现 3 次以上，或复制实现已经漂移。
- 分层违规：UI 依赖数据层内部；循环依赖；高 fan-in 的 `utils` 垃圾抽屉。
- 死代码：未导出且未使用的模块；已全量发布的 feature flag 仍保留分支；无说明注释代码；manifest 中不再导入的依赖。
- God module：文件远大于仓库中位数且被大量模块依赖；函数参数过多或条件嵌套过深。
- 同一仓库存在多套数据请求、错误处理或样式模式。优先项目最近收敛的模式，并规划合并。
- 抽象失配：只有一个实现的提前抽象；或同一变更总要同步修改多个文件却没有正确边界。

## 3. 依赖与迁移

- 核心框架 / runtime 落后主要版本，且继续停留会带来 EOL、安全修复截止或生态不兼容；不要报告每个 minor。
- 正在使用已公布移除时间的 deprecated API。
- 关键路径依赖多年未发布或仓库已归档。
- 同一问题使用重复依赖，例如两个日期库、两个 HTTP client。
- monorepo 的 lockfile / manifest 漂移或版本固定不一致。
- 每个迁移候选都估算会触及多少文件；爆炸半径决定工作量和值不值得做。

## 4. 开发体验与工具

- 缺失或损坏的 typecheck、lint、formatter、pre-commit、editorconfig。
- 反馈环过慢：dev server / tests 启动以分钟计；没有 watch；CI 无缓存。报告前先测量。
- 上手摩擦：README 步骤错误或不完整；必要环境变量无文档；缺 `.env.example`。
- Agent 将执行计划的仓库缺 AGENTS / CLAUDE 时，可建议最小索引并给出大纲；不要写成大篇治理文档。
- 服务日志无结构、无 request / correlation ID，调试必须先改代码。

## 5. 文档

默认优先级最低；只有缺失造成具体成本时才报告：

- 发布包的公开 API 没有参考文档。
- 活跃争议区域的架构决策无法重建。
- 文档已经错误并误导用户，例如 setup 或 API 示例无法运行；错误文档比缺文档更差。
