# 方向审计手册

方向审计讨论项目接下来适合成为什么，不把产品选项伪装成缺陷。每条建议必须引用仓库证据；“加暗色模式”“加 AI”这类可套在任何项目上的建议是噪声。

## 证据来源

- **未完成意图**：同一主题的 TODO / FIXME、未完成 rollout 的 feature flag、stub / 半成品模块、注释掉的功能、Git 历史中停在中途的建设。
- **承诺但未交付**：README / roadmap 已承诺但代码没有；CLI flag 或配置是 no-op；PRD / `PRODUCT.md` 描述的用户和用例尚未落地。产品意图文档强于推测，且不得重提决策文档已拒绝的方案；应报告两者矛盾。
- **表面不对称**：有 export 无 import、有 create 无 bulk-create、只发 webhook 不接收、CRUD 缺一项、内部代码手写绕过本应公开的 API。
- **相邻可能性**：现有架构使某能力异常便宜，例如只差一个接口的插件能力、只差一条 route 的公开 API、数据模型已经支持的集成。
- **值得产品化的摩擦**：文档、示例或 issue 显示用户长期手工完成的外围工作，项目可以合理吸收。

## 评价方式

方向发现沿用 [audit-core.md](audit-core.md) 的 Finding format，但：

- **影响**写产品 / 用户价值：谁需要，为什么是现在。
- **置信度**表示证据扎根程度，不代表维护者一定应选择它。
- 工作量只做诚实的粗估并明确说明。
- 对用户选中的方向通常写设计 / spike 计划：调查、原型、API 边界、开放问题，而不是一次建完全部功能。

方向建议必须与缺陷表分开。完整审计最多给 2–4 条；`next` / `features` / `roadmap` 变体给 4–6 条。每条用两三句话说明证据、收益、成本和不建议现在做的理由；允许结论是“不值得做”。
