# 核心审计手册

用于 `quick`，以及正确性、安全、测试聚焦审计。按仓库规模调整深度：2K 行 CLI 不应套用 500K 行 monorepo 的扫描量。

发现必须有证据。“可能某处存在 N+1”不是发现；`orders/api.ts:142` 在订单项循环中逐项查询才是。

## 1. 正确性 / 缺陷

这是可信度最高的类别：报告通过阅读确认的真实问题，不报告猜测。

- 错误处理：吞掉异常、空 catch、关键路径只 `console.log`、UI 缺失错误状态。
- 异步风险：未 await 的 Promise、共享状态竞态、缺少取消或清理，例如 React effect 陈旧闭包和未移除监听器。
- null / undefined 流：可能为空的值被非空断言，optional chaining 掩盖必须存在的值，数组索引未检查。
- 边界条件：off-by-one、空集合、时区 / locale 假设、计数器或 ID 整数溢出。
- 状态机：类型允许不可能状态；状态枚举分支未处理；`default` 静默 no-op。
- 并发：共享资源 check-then-act；多次写入缺事务；webhook、队列等重试路径不幂等。
- 类型逃逸：`any`、`as`、`@ts-ignore` 集中出现，意味着编译器约束被绕过。
- 资源泄漏：句柄、连接、订阅未关闭，缺少 `finally`。

## 2. 安全

只报告代码直接支持的证据。以防御性维护描述代码模式、生产影响、配置 / 代码 / 测试层面的修复方向；不得给出可运行攻击字符串或逐步滥用方法。

**密钥规则：** 发现和计划绝不复制密钥值，只写凭据类型和 `文件:行号`；修复必须包括删除、轮换和安全配置路径。已经提交过的密钥即使删除也已失效。

**设计行为不是发现：** `https_proxy` / `NO_PROXY`、`~/.netrc`、本地开发工具调用已配置的包管理器等平台惯例通常是有意行为。ADR 已记录的权衡也不是缺陷；但代码与 ADR 已漂移时，应报告“决策漂移”。

- 凭据卫生：硬编码 key / token / password、提交的 `.env`、日志或历史存储中的凭据。
- 数据进入解释器或特权 API：请求数据拼接 SQL / shell；用户内容进入 HTML sink；动态执行运行时输入；请求路径进入文件系统。
- 访问控制：服务端缺身份验证；只在客户端鉴权；按 ID 访问对象却不校验 owner / tenant；状态变更缺 CSRF / 请求真实性校验。
- 输入合同：请求体无 schema；上传缺类型、大小、存储边界；请求对象整体写入持久化模型导致 mass assignment。
- 依赖状态：只读运行生态审计命令；只报告影响可达运行时或构建 / 发布路径的 critical / high 漏洞，不制造低价值告警噪声。
- 生产配置：携带凭据时 CORS 过宽；敏感 Web 表面缺 CSP 等响应头；cookie 缺 `HttpOnly` / `Secure` / `SameSite`；生产启用 debug / verbose。
- 数据最小化：日志含 PII 或敏感运维数据；响应返回 stack trace 或内部错误细节。

## 3. 测试覆盖

目标不是覆盖率数字，而是识别哪些危险路径没有可信验证。

- 映射金钱、认证、数据写入和项目核心功能等关键路径，检查是否零覆盖或只有表面断言。
- 高频改动模块没有测试，是重构高风险区；优先建议 characterization tests。
- 检查测试质量：无意义断言、只测 mock、无人审阅的 snapshot、真实时钟 / 网络 / 顺序依赖导致 flaky。
- 检查测试层缺口：只有 unit 没有 API 边界 integration，或所有简单逻辑都依赖缓慢 E2E。
- 检查是否有一条命令能判断代码库可用。没有时，验证基础设施通常是发现 #1，也是高风险改动的前置计划。

## 发现格式（Finding format）

每个类别、每轮审计都使用以下格式：

```markdown
### [类别-NN] 使用祈使句的短标题

- **证据**：`path/file.ts:123` — 此处事实的一句话说明。每项给 2–5 个最强位置；同模式很多时写“另有约 N 处”。
- **影响**：具体会发生什么或持续付出什么成本，例如“订单列表每次渲染发出 1+N 次查询”，不是“性能不好”。
- **工作量**：S（数小时）/ M（约一天）/ L（多天），包含修复和测试。
- **风险**：LOW / MED / HIGH，并说明修复可能破坏什么。
- **置信度**：HIGH（已读代码并确认）/ MED（信号强，仍需验证）/ LOW（气味，需调查）。LOW 只能生成调查计划，不能写成确定修复。
- **修复草图**：1–3 句，足以诚实估算工作量，但不是完整计划。
```

## 排序规则

按 **杠杆率 = 影响 ÷ 工作量，再按置信度和修复风险折扣** 排序。平手时：

1. 能解锁其他计划的验证基线或 characterization tests 优先。
2. HIGH 置信度安全问题优先于同杠杆非安全问题。
3. 优先选择验证路径清楚、执行模型更容易完成的修复。
4. “不值得做”是有效结论；用一行理由记录，避免以后重复审计。
