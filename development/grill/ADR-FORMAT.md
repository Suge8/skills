# ADR 格式

ADR 存放在 `docs/adr/`，并使用连续编号：`0001-slug.md`、`0002-slug.md`，以此类推。

懒创建 `docs/adr/` 目录，只有第一个 ADR 被需要时才创建。

## 模板

```md
# {决策短标题}

{1-3 句话：背景是什么，我们决定了什么，为什么这么决定。}
```

就这些。一个 ADR 可以只有一个段落。价值在于记录“做过这个决策”和“为什么”，不在于填满各个章节。

## 可选章节

只有它们能带来真实价值时才加入。大多数 ADR 不需要这些章节。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`），适合决策被重新讨论时使用
- **Considered Options**，只有被拒绝的替代方案值得记住时才写
- **Consequences**，只有不明显的下游影响需要点明时才写

## 编号

扫描 `docs/adr/` 中已有的最高编号，然后加一。

## 什么时候提议写 ADR

必须同时满足三点：

1. **难以回退**，以后改变主意的成本有意义
2. **缺少上下文会让人意外**，未来读者看到代码会想“为什么会这么做？”
3. **来自真实权衡**，存在真正的替代方案，而你因为具体理由选择了其中一个

如果决策容易回退，就跳过，你到时直接回退就行。如果它不意外，没人会问为什么。如果没有真实替代方案，除了“我们做了显而易见的事”以外就没什么可记录。

### 哪些内容符合条件

- **架构形态。** “我们使用 monorepo。”“写模型是事件溯源的，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。”
- **带有锁定成本的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库都要记，只记那些替换需要一个季度的选择。
- **边界和范围决策。** “Customer 数据归 Customer context 所有；其他 contexts 只通过 ID 引用它。” 明确的“不做什么”和“做什么”一样有价值。
- **刻意偏离显而易见路径。** “我们不用 ORM，而是手写 SQL，因为 X。” 任何合理读者会默认相反选择的地方都要记录。这能阻止下一个工程师去“修复”一件本来就是刻意为之的事。
- **代码中看不出来的约束。** “因为合规要求，我们不能用 AWS。”“因为合作方 API 合约，响应时间必须低于 200ms。”
- **拒绝理由不明显的替代方案。** 如果你考虑过 GraphQL，但因为微妙理由选择了 REST，记录下来，否则六个月后又会有人建议 GraphQL。
