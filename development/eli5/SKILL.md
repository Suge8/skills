# ELI5

把被引用的规范、变更或机制转化为准确的心智模型，读者是技术人员，但不生活在这份代码里。平实的语言，完整的精度：简化讲法，绝不简化论断。

## 口吻

其他 Skill 需要让没参与过这项工作的人读懂产出时，会指向这里。读者是技术人员——伪代码和精确论断都能落地——但他们没读过任何代码，也没看过本次会话的任何消息：没有 diff，没有记录，没有工作过程中临时发明的标签。写 ELI5 意味着：

- 用具体场景从头走到尾——触发事件、今天会发生什么、变更（或未实现的替代方案）会怎样——而不是抽象地描述属性。场景要覆盖计划的每一部分：一条走不完就多走几条，但每一条都是完整走法，不退回抽象罗列。
- 每个术语首次出现时定义；绝不依赖规范、代码或会话里发明的标签。
- 用小而具体的例子，但不用类比替代精确论断。
- 解释控制流、顺序或时序时写伪代码。散文描述「什么时候触发」读起来合理却藏着漏洞；五行伪代码能把门槛摆到明面上，让读者看见你漏掉的情形。写在决策层，不写实现层——条件及其顺序，而不是真实函数签名。需要它的信号：你的文字里出现了「仅当」「之前」「除非」「一旦」，而读者仍说不出第二次调用会发生什么。
- 检验：文本脱离 diff、规范和会话记录也能独立成立。读者若需要问「这一段再解释一下」，就失败了。

## 流程

1. 读完被引用的完整产物；规范本身不足以确定行为时，检查当前的 owner 代码。没有指定产物时，解释本次会话的当前变更（工作树或分支 diff）。把今天已存在的和仅是提议的分开。
2. 通过用户或运维后果解释问题，包括当前设计为什么会产生它。
3. 把方案解释为一条简单的 before/after 数据流。每个组件按职责引入，不按文件名或内部符号。
4. 穷举 schema 与持久契约的变化：新增、修改、删除、重置、刻意不动。游标或线格式切换影响到存储数据或读取方时也要列入。没有 schema 变化时明确说出来。

解释对象是现有机制而不是变更时，第 2、3 步换成：当前的行为是什么，场景走到底，边界和契约在哪里。

## 输出

按顺序使用这些标题：

1. `问题`
2. `方案`
3. `Schema 与契约变化`

解释现有机制时对应为 `现状`、`场景走法`、`边界与契约`。

结尾用一句短话说明变更之后用户应当注意到什么。

### 形式

默认产出一个自包含 HTML 并 `open` 给用户看；只有两句话能说完的问题才只用文字。

- HTML 是视觉解释器，不是文章：大图形、少文字，文字只做标注。三个标题对应三个区块。
- 具体场景贯穿全页，多条场景时分区块并排；用真实的名字和数据，不用占位符。
- 每个要点选能讲清它的最小视图；变更优先用 diff 形状表达，形状跟着主题走（调用树、文件树、状态流），而不是并排两张完整图。
- 边界、状态、异常路径用颜色分区。
- 中文正文用 PingFang SC，字重 ≥ 500；桌面和移动端都能看。

## 规则

- 以行为和边界为先；只有在澄清所有权或契约时才提实现名称。
- 区分权威记录与派生索引、缓存、摘要和展示层分组。
- 直接点出破坏性重置、迁移要求、兼容行为、最终一致性和有意的数据丢失。
- 不要因为一处 schema 变化只在运维层面而非用户可见就略过它。
