# Flow Better Test

目标：让 Agent 能独立、重复地证明行为正确，减少人工验收和假完成。

## 先分流

只走一个主分支：

1. 已知 bug、错误输出、性能回归或 flaky，需要复现、定位和修复 → **Diagnose**。本 skill 不做根因排查；Diagnose 产出的回归用例直接进入现有测试链。
2. 项目没有合格测试链 → **首次建链**。
3. 测试链已能运行，但新增或改变的正常行为没有覆盖 → **补覆盖**。
4. 自动化碰不到目标行为 → **取证兜底并记录测试债**。

## 首次建链

先检查现有依赖、测试入口和相邻项目模式，再判断测试链是否同时满足：

- Agent 可独立运行，不需要人肉点击；
- 无头或隔离运行，不抢用户的输入设备；
- 结果可重复，不依赖 sleep、实时网络或执行顺序；
- 断言具体行为，不是“没崩就算过”。

不满足时，按 [references/toolchains.md](./references/toolchains.md) 选择项目已有生态中的最小方案；只有项目内没有事实源且 API 或选型不确定时，才查当前官方资料。默认不新增生产依赖。

最小交付只有两部分：一个可运行的 harness，以及当前最需要的一条行为用例。不要一次铺完整套件。

首次校准必须证明信号真实：

1. 运行持久 harness 的正式入口，positive control 必须 exit 0；命令不存在、导入错误或 0 tests 都不算通过，先修入口并重跑至绿。
2. 在同一持久测试文件里临时反转一条断言，再运行同一 harness 入口，确认测试进程非零退出并报告预期失败；inline 一次性脚本或无关失败不算校准。
3. 精确还原该断言，再运行同一入口至全绿。

完成门：工具轨迹必须按顺序出现“同一 harness 绿 → 断言反转 → 红 → 断言还原 → 绿”。禁止用测试框架常识或口头声明替代实际运行。negative control 只校准测试 harness，不得修改业务代码制造 bug，也不得留在工作区。

## 已有链补覆盖

1. 读本次行为变化、现有测试入口和 1–3 个相邻用例。
2. 在最近的正确 seam 增加一条行为断言；不要断言私有实现、固定话术或夹具巧合。
3. 运行最窄受影响测试；接口或配置变化时再跑对应上层测试。
4. 报告具体命令与通过数量。

这里**不要求先出现失败测试**。新增的正常行为可能已经实现，补上的测试第一次运行就通过是合法结果；不得为了套红绿流程临时写错断言。若测试暴露真实缺陷，转 Diagnose 复现和定位。

## 自动化够不到时取证

按接近用户真实路径的顺序选最短方法：

1. **flow-browser-use**：页面、DOM、截图、console、network；
2. curl 或 CLI：直接调用并断言响应内容；
3. 带具体断言的日志；
4. **better-computer-use**：桌面应用或真机兜底，读取控件并截图；
5. 都不可行：给用户“打开哪里 → 做什么 → 应看到什么”的最短清单，明确标注未验证。

证据必须来自本次执行。取证后记录自动化缺口；同一路径第二次需要人工取证时，应转成建链任务。

## 质量红线

- 快：最窄测试应快到每次改动都愿意运行。
- 确定：固定 seed、时钟和网络；用条件等待，不用 sleep。
- 精确：一条用例验证一个行为，失败信息能直接定位合同。
- 干净：无永久 skip、临时错误断言、僵尸进程或测试生成物。
